# 莱赛尔平台：Apifox 导入与接口测试

当前代码的接口文件已生成。第一次先导入核心测试集合，再导入本地环境；测试按编号从 01 开始。普通用户和管理员登录的后置脚本会自动保存 JWT，下单后也会保存订单 ID。

## 先导入这两个文件

| 文件 | 用途 |
| --- | --- |
| `lesaire.core.postman_collection.json` | 推荐先导入：39 个按序请求，含正常流程、错误场景、JWT 提取和断言 |
| `lesaire.local.postman_environment.json` | 随后导入：本地 URL、公开演示账号以及等待脚本写入的变量 |
| `lesaire.images.postman_collection.json` | 可选：4 个图片手动请求，选择自己的照片后单独执行 |
| `lesaire.openapi.json` | 可选：完整 14 个接口操作的 OpenAPI 3.0.3 文档，含字段约束、请求/响应结构及示例 |
| `测试用例清单.md`、`验证结果.json` | 阅读用：预期状态与本地实测结果，不用于导入 |

上面的 JSON 均在 `D:\lsecode\docs\apifox`。不要把整个文件夹一起导入，先选择需要的集合和环境即可。OpenAPI 是另一份标准接口文档，初次测试不必同时导入它。

## 对照你截图里的窗口操作

1. 点击导入弹窗中的“文件”，选择 `D:\lsecode\docs\apifox\lesaire.core.postman_collection.json`。格式为 Postman Collection v2.1。
2. 在导入预览中保留全部请求/用例和前后置脚本；同一方法、同一路径的正常/错误请求都是不同测试用例。若出现覆盖与保留选项，保留测试用例，避免只留下最后一条请求。
3. 在预览的“环境”部分勾选集合生成的环境，再确认导入。
4. 进入创建好的项目，通过“项目设置 → 导入数据”，按 Postman 格式导入 `lesaire.local.postman_environment.json`。调试时选择“莱赛尔本地接口测试”环境。
5. 核对环境服务的前置 URL 是 `http://127.0.0.1:8080`，环境变量 `baseUrl` 也是这个值。不要选择 Mock 地址。
6. 确认 IDEA 或后台脚本已启动项目；浏览器访问 `http://127.0.0.1:8080/api/catalog` 应能看到目录 JSON。
7. 先执行 01、02、03，再顺序执行剩余请求。请求中已经有 JWT 请求头，后置脚本会验证 HTTP 状态及关键字段。

Apifox 官方说明支持分别导入 Postman 集合与环境，导入后需要选择相应环境；`pm.environment.set`、`pm.test` 和 `pm.expect` 可用于提取变量与断言。参见[导入 Postman](https://docs.apifox.com/import-postman)和[脚本 API](https://docs.apifox.com/postman-script-api)。

如只希望先导入标准接口目录，选择 `lesaire.openapi.json`，使用“以可视化界面维护接口”，并导入 Servers 为环境和 Bearer 鉴权配置。该文件不包含核心集合的 39 个前后置测试脚本。操作依据见[导入 OpenAPI/Swagger](https://docs.apifox.com/import-openapi-swagger)。

## 测试顺序和讲解重点

| 编号 | 测什么 | 正确结果 |
| --- | --- | --- |
| 01–03 | 目录、普通用户登录、管理员登录 | 200；自动保存真实目录编码和两个 token |
| 04–14 | 用户资料、订单分页、报价及输入/权限错误 | 正常 200；缺少或无效 JWT 401，权限不足 403，输入错误 400 |
| 15–26 | 新订单、重复提交、制作状态、收货 | 下单 201；重复返回同一 ID；按顺序更新 200，跳步 400 |
| 27–28 | 创建一笔独立订单并取消 | 201 → 200，状态变为 CANCELLED |
| 29–36 | 注册、重复注册、量体保存、订单归属、退出 | 注册 201，重复 409；操作他人订单 404；退出后旧 token 401 |
| 37–39 | 退出演示账号并验证撤销 | 退出 200；旧用户 token 401 |

完整运行会新增一个“Apifox接口验收用户”、一个完成订单和一个取消订单，订单备注注明无需实际制作。测试只推进本轮自动保存的订单 ID。量体成功保存使用新注册用户，不覆盖演示用户档案；第 13 条是无效量体请求，不会保存。

状态流转：`PENDING → CUTTING → SEWING → QUALITY → SHIPPED → COMPLETED`。取消只允许待确认订单；普通用户确认收货只允许已发货订单。

讲解时可以说：“我通过接口测试验证三层之间的数据传递。先登录获取 JWT，再选配报价、下单，最后推进状态与收货；同时故意传错参数、缺少令牌和越权操作，检查后端是否拒绝。”

## 变量怎样传递

| 变量 | 谁写入 | 谁使用 |
| --- | --- | --- |
| `baseUrl` | 本地环境初始值 | 全部请求的服务地址 |
| `productId`、`fabricId`、`colorId`、`expectedTotal` | 01 目录响应脚本 | 报价、下单及价格断言 |
| `userToken` | 02 普通用户登录 | 用户资料、订单和用户状态操作 |
| `adminToken` | 03 管理员登录 | 管理员订单列表与制作状态操作 |
| `requestKey`、`orderId` | 15 下单前/后脚本 | 16 重复提交与后续状态操作 |
| `cancelRequestKey`、`cancelOrderId` | 27 下单前/后脚本 | 28 取消订单 |
| `registrationPhone`、`otherUserToken` | 29 注册前脚本、31 登录后脚本 | 注册重复、新用户量体和归属测试 |

注册返回 `AccountView`，不会直接返回 token；第 31 条才登录。登录响应的账号字段是 `account`，分页数组字段是 `items`，没有 `data` 包装。脚本已按这些真实字段编写。

认证请求头已填成 `Authorization: Bearer {{userToken}}` 或管理员变量；环境里的 token **只存令牌本身**，不要再加 `Bearer `。初始文件里的 token 都为空，不包含可用登录令牌或数据库密码。

## 图片单独手动测试

导入 `lesaire.images.postman_collection.json` 后选择同一份本地环境：

1. 执行“图片01”登录管理员。
2. “图片02”的 Body 选择 `form-data`，找到 `file` 文件字段，点击选择自己的 JPG/PNG。不要手动设置 multipart 的 Content-Type，Apifox 会自动生成 boundary。
3. `styleCode` 默认 `RS-CF-001`，可改为目录返回的其他款式 ID。发送成功后，返回对象的 `imageUrl` 会自动保存到环境。
4. 执行“图片03”公开读取照片，再刷新网页检查款式图片；最后“图片04”退出。

成功上传会替换该款式图片地址。文件限制为 5 MiB，每边不超过 6000 像素，总像素不超过 1200 万；需要真实、可解码的 JPG/PNG。自动核心集合不包含上传操作，所以批量跑核心测试不会替换照片。

## 常见问题

- 返回 401：先重新登录。服务重启、JWT 到期、执行退出后旧令牌都会失效。完整重跑从 01 开始。
- 提示变量未定义或 URL 不正确：选中本地环境，并确认前置 URL 与 `baseUrl`。先执行对应的登录、目录或下单请求。
- 单独再次执行 15：会生成新的 requestKey，创建新订单；验证重复提交必须点 16。单独再次执行 29 同样会注册新手机号。
- 状态更新返回 400：检查是否按状态顺序执行。完整重跑会生成新的测试订单，不能对已完成订单从裁剪重新开始。
- 报价返回 400：`fabricId` 和 `colorId` 必须匹配；数量 1–5。`neckline` 填 `round`，是兼容必填字段，当前不参与衬衫计价。
- 图片读取 404：先成功上传，再使用真实 `imageUrl`；文档里的示例文件名不代表实际存在。
